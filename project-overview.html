Real-Time Cybersecurity Event Analytics Platform

This is a complete guide to the Group 4 project: what it does, how each part works, why we built it that way, which edge cases it handles, and where its limits are. Read it top to bottom. Each section builds on the one before it.

1What problem we are solving

Every company runs computers that get attacked: people guess passwords, scan for open ports, try to inject code into websites, or flood a server with requests. Each of those computers writes logs, lines like "someone at IP X failed to log in as user Y at 10:03:21".

A SIEM (Security Information and Event Management system) collects all of those logs in one place and watches them for patterns that mean "attack". Splunk, Elastic Security and Microsoft Sentinel are well-known commercial SIEMs.

A traditional SIEM stores the logs first and runs searches on them every few minutes, so an attack can be well under way before anyone notices. Our project is a stream-first SIEM: it checks every event the moment it arrives, as it flows past, and raises an alert within about 50 milliseconds. All the data is also stored for later analysis.

In one sentenceWe built a small but complete security operations centre on a laptop. One side attacks a fake company network, the network logs what happens, a streaming data pipeline detects the attacks in real time, stores everything in two kinds of storage, and a dashboard explains what happened. It even grades how well it did.

The project is a data engineering project first. Security is the application, and the interesting parts are the pipeline problems underneath: ordering, duplicates, late data, crash recovery, storage layout and freshness.

3The life of one event, start to finish

The easiest way to understand the system is to follow one failed login from an attacker all the way to the dashboard.

  1. The attacker acts. You click "Brute Force" in the red console. The simulator creates an attacker with its own IP address, say 127.66.0.5, which sends POST /login with a wrong password to the target web app.
  2. The victim logs it. The target app answers "401 wrong password". It writes a security event recording the IP it saw on the connection, the username, and the result fail. The attacker doesn't write this log; the defended system does.
  3. The shipper forwards it. The event goes into the log shipper's queue. A worker POSTs it to the ingest API and retries with backoff if ingest is busy or down.
  4. Ingest checks it. The ingest API validates the event against a fixed schema (the contract) and stamps ingest_time. It then writes the event to the Kafka topic security.events.raw, using the source IP as the key. A broken event goes to a dead-letter topic instead, together with the reason.
  5. Kafka fans it out. Three independent readers (consumer groups) each get their own copy of the event: the stream processor, the lake writer and the dashboard bridge.
  6. The processor detects. The processor drops the event if it is a duplicate or too late. Otherwise it places the event in the right 10-second time slot and updates every rule that cares about it. On the 5th failure from this IP for this user within 60 seconds, the brute_force rule crosses its threshold and an alert fires immediately, about 50 ms after the event arrived.
  7. The alert travels on. The alert goes to the security.alerts topic. The dashboard pushes it to the browser over a WebSocket. The warehouse writer saves it in Postgres and attaches it to an incident.
  8. The raw event is archived. Separately, the lake writer collects events for up to 30 seconds and writes them as a Parquet file in a folder for that hour.
  9. An AI explains it. Once the incident has been quiet for 8 seconds, the summariser asks Gemini for a plain-English summary and saves it. If Gemini is unavailable, it uses a template instead.
  10. The system grades itself. The simulator also published what it launched (the ground truth). The scoreboard compares that with the alerts: was the attack caught, how fast, and how much of it happened before the alert?

4Red team: the attack simulator

What it is

The simulator is a Python FastAPI service that pretends to be a whole company's worth of people: ordinary employees doing their jobs, and attackers. It sends real network traffic (HTTP requests and TCP connections) to the target and the sensor. It never writes security logs itself.

The trick: 127.x addresses

On Linux, every address from 127.0.0.1 to 127.255.255.254 is loopback, meaning "this same machine". A program can choose which of those addresses its connection comes from. We use that to give every simulated machine its own real IP, all on one laptop:

WhoAddresses
Employees (normal users)127.0.1.x
Office behind one NAT router127.0.2.x
IT administrators127.0.3.x
Server (target app + sensor ports)127.0.10.1
Workstations (for host sweeps)127.0.10.2 to .21
Attackers127.66.0.x (each campaign gets a fresh IP)
Botnet127.77.N.x
Why this mattersThe target sees the attacker's IP from the kernel, the same way a real server would. Nothing is "reported" by the attacker, so the source IP cannot be faked through a header. This also lets us tell attackers, employees and admins apart, which the self-evaluation depends on.

Background traffic

While it is switched on, 24 employee hosts make normal requests about 5 times a second: logging in, searching and exporting. This is the "noise" that attacks hide in. A good detector stays silent on it, and ours raised 0 alerts on employee traffic.

Ground truth

Every time a scenario starts or finishes, the simulator publishes a record to its own Kafka topic, security.sim.campaigns. The record holds the scenario name, the attacker IPs, start and end times, the expected rules, and whether it is malicious. The detector never reads this topic. Only the scoreboard does.

5Defended systems and the log shipper

Target web app

A small FastAPI website at 127.0.10.1:8002. It is deliberately unprotected (no rate limiting, no lockout) so attacks actually happen. It has:

  • /login: a username and password check against a small set of users
  • /api/search: a search endpoint where injection payloads arrive
  • /api/export: data export that needs a bearer token, the "stealing data" step

A middleware writes one security event per request, with the peer IP, the user, and the status (success, fail or denied). It also stores the decoded request line in raw_payload, so injection patterns can be matched later.

Network sensor

A web app only sees traffic that reaches its own port. A port scan mostly hits ports where nothing is listening, so the website would never know. The sensor fills that gap:

  • Open ports 2222 (SSH), 3306 (MySQL), 6379 (Redis), 8080 and 9200 answer with a realistic banner and are logged as success.
  • 15 closed ports immediately reset the connection (an RST packet) and are logged as denied.
  • Port 3389 (remote desktop) on 20 workstations catches horizontal host sweeps.

Log shipper

Both the target and the sensor use the same shipper, our small version of what Filebeat or Fluent Bit do in real companies:

  • A bounded queue of 10,000 events, so memory can't grow forever. If the queue is full, the event is counted as dropped, not silently lost.
  • 8 workers POST events to ingest.
  • Retry with backoff when ingest replies "503 busy" or the connection fails.
  • Counters for sent, rejected, failed and dropped events, which the pipeline-health page reads.

"Unreliable network" (chaos) mode

Real networks misbehave, and a demo where everything is perfect proves nothing. When chaos mode is on, the shipper deliberately:

  • sends 10% of events twice, as a retry after a lost acknowledgement would. This tests deduplication.
  • delays 10% of events by 2–8 s, so they arrive out of order but still in time. This tests event-time windows.
  • delays 2% of events by 90 s, a backlog flushed after an outage, which is too late. This tests the watermark.

6Ingest API and the event contract

The ingest API (port 8000) is the single front door into the pipeline. Its flow is validate → stamp ingest_time → write to Kafka → reply 202.

The contract

Every event must match a fixed JSON schema (contracts/event.schema.json, version 1, frozen):

FieldMeaningRules
event_idUnique IDUUID, required. Used for dedup.
event_timeWhen it happened at the sourceRequired, and must include a timezone offset. Drives all windowing.
ingest_timeWhen it arrivedSet by the server, overwriting any value the client sent.
source_typeKind of logauth, network or api
src_ipWho did itRequired. Becomes the Kafka key.
dest_ip_portWhat they touchedip:port, optional
userAccount involvedOptional
statusOutcomesuccess, fail or denied
raw_payloadExtra detailsFree-form, for example the request path
Why a strict, frozen contract
  • Unknown fields are rejected, so if a source changes its log format the change shows up immediately at the door instead of silently corrupting reports weeks later.
  • A timezone is required because "10:03" without one is ambiguous, and every window depends on time.
  • Invalid events are not thrown away. They go to a dead-letter queue (security.events.dlq) with the reason, so the bad input is kept as evidence and can be debugged.

7Kafka: the backbone

Kafka is a durable, append-only log. Producers add messages to the end, and consumers read at their own pace, each remembering its position (its offset). We run Kafka 4.3.1 in KRaft mode, which needs no ZooKeeper.

TopicPartitionsWritten by → read by
security.events.raw3, key = src_ipingest → processor, lake writer
security.events.dlq1ingest, processor (rejected events plus reason)
security.alerts1processor → warehouse writer, dashboard
security.aggregates1processor → warehouse writer
security.pipeline.metrics1processor → warehouse writer, dashboard
security.sim.campaigns1simulator → warehouse writer (scoreboard only)

Key design decisions

Key = source IP

Kafka keeps order only within a partition. Keying by IP puts all events from one attacker in one partition, in order, so "5 failures then a success" is seen in the right sequence.

One consumer group per job

The processor, lake writer, warehouse writer and dashboard each read independently. If Postgres is slow, detection doesn't wait. Each layer can be restarted or replayed alone.

acks=all + idempotent producers

A write counts as done only once Kafka has stored it. Idempotent producers stop network retries from creating duplicate copies inside Kafka.

Auto topic creation off

Topics are created explicitly by infra/create-topics.sh, so a typo in a topic name fails loudly instead of creating a ghost topic.

8The stream processor (the brain)

The processor follows the steps from our Lab 3 design: parse & validate → place into event-time windows → advance the watermark → drop duplicates → evaluate rules → emit alerts. It is plain Python with no Flink or Spark, so every mechanism is visible and explainable.

8.1 Windows and panes

Attacks are about counts over time ("5 failures in a minute"), so we need windows. We use sliding windows 60 seconds long that start every 10 seconds, so a burst is never split awkwardly across two windows.

A naive implementation copies each event into all 6 windows that overlap it. Instead, we split time into 10-second panes. Each event goes into exactly one pane, and a window is simply 6 consecutive panes added together.

Figure 2. The red event belongs to windows A, B and C but is stored only once, in pane 30–40.

Event time, not arrival time: windows use event_time, when the thing actually happened. An event delayed in the network still counts in the minute it belongs to.

8.2 Watermark: when is a window "done"?

With event time, the processor can never be completely sure no more events for 10:03 will arrive. The watermark is its rule for deciding: "I assume nothing arrives more than 10 seconds late."

watermark = newest event_time seen − 10 seconds
a window closes when the watermark passes its end
  • An event for a window that has already closed is late. It is dropped and counted, so the count is visible on the dashboard.
  • Idle stream: if nothing arrives for 5 s, the watermark follows the wall clock, so the last windows still close.
  • Broken clocks: an event more than 60 s in the future goes to the DLQ. Otherwise it would jump the watermark forward and make every honest event look late.
Trade-offA bigger lateness allowance accepts more late data but closes windows, and frees memory, later. 10 s suits a LAN. The 2–8 s chaos delays pass, and the 90 s backlog is dropped, which is exactly what the demo shows.

8.3 Deduplication

Our delivery is at-least-once: retries can deliver the same event twice. The processor remembers event_ids, but only for windows that are still open. Once a window closes, its IDs are forgotten. A duplicate of an older event would be late anyway, so memory stays bounded by the window length no matter how long the system runs.

8.4 The 10 detection rules

Each rule has four parts: which events it looks at, how it groups them (the key), what it measures in a window, and a threshold. Each one is tagged with a MITRE ATT&CK technique, the industry-standard catalogue of attacker behaviour.

Injection signatures are regular expressions run on the decoded request. They cover SQL (' OR, UNION SELECT), OS commands (; cat), path traversal (../), NoSQL operators ([$ne]), templates ({{ }}), scripts (<script), LDAP filters and CRLF header injection. Reaching 3× a threshold raises the alert one severity level. Each threshold can be changed with an environment variable.

Why simple rules instead of machine learning?Rules are explainable ("5 failures in 60 s from this IP"), need no training data, and an analyst can trust them. We only wrote rules our schema can really support; for example, there is no "impossible travel" rule because we have no geo-location field.

8.5 Early alerting: our biggest latency win

A basic windowed system alerts when a window closes, which can be up to 60 s plus 10 s of lateness after the attack started. Every one of our rules measures something that only grows (a count, or a number of distinct values), so once it crosses the threshold it can never drop back below it. We can therefore alert the instant the threshold is crossed with no risk of having to take the alert back.

One alert goes through up to three versions, all under the same alert ID:

  • early the moment the threshold is crossed
  • escalated at 3× the threshold, with a higher severity
  • final when the window closes, with the exact final count

No alert storms: sliding windows overlap, so a naive version would raise 6 alerts for one 20-second attack. While one window has alerted for a given rule and key, overlapping windows are suppressed. One attack gives one alert.

The alert ID is deterministic: a UUID5 hash of the rule, key and window. The same alert always gets the same ID, so writing it to Postgres again simply updates it (an upsert). This is how "at-least-once delivery" becomes "effectively once" in the results.

8.6 Crash safety: the commit protocol

A Kafka consumer says "I'm done up to offset N" by committing. Commit too early and a crash loses events. Commit too late and a crash repeats work. Our rule:

  • Commit only up to the oldest event still inside an open window, because those events are still needed if we crash.
  • Commit only after Kafka has acknowledged all the alerts we produced.
  • Save a small checkpoint ("windows before time T are already closed") in the commit metadata.

After a restart, the processor re-reads Kafka from the committed point, rebuilds its open windows, and uses the checkpoint to avoid re-emitting closed windows. In testing, a restart lost 0 events and re-emitted 0 alerts.

Metrics the processor publishes (every 5 s)

Events per second, consumer lag, watermark delay, detection latency (p50, p95 and p99 over the last 500 alerts), per-stage latency, and counters for accepted, duplicate, late, invalid and alerts by rule. We report percentiles, not averages, because for alerting the slow tail is what hurts.

9Data lake: every raw event, in Parquet

The lake writer is a separate consumer group that saves every raw event for later investigation, using cheap, compressed, analytics-friendly files.

  • Format: Apache Parquet with Snappy compression. Parquet is columnar: all src_ip values are stored together, all status values together, and so on. A query that needs only 2 columns reads only those 2, and similar values next to each other compress well. Measured: about 5.2× smaller than raw JSON.
  • Layout: Hive-style folders data_lake/year=2026/month=11/day=12/hour=14/, based on event time in UTC, so a late event still lands in its true hour. A query for "2 pm yesterday" opens only that folder. This is called partition pruning.
  • Micro-batches: a file is written every 5,000 events or 30 seconds, whichever comes first. Writing one file per event would create millions of tiny files.
  • No half-written files: each file is written to a temporary name, then renamed. A rename is atomic, so readers never see a partial file.
  • Provenance: every row keeps its Kafka partition and offset, so you can trace it back. Each file also records the raw JSON size in its metadata, which is how we measure compression.
  • Delivery: offsets are committed after the file is written. A crash between the two can write a row twice, so readers deduplicate on event_id, as the scoreboard does.

11Incidents: turning alerts into stories

An analyst doesn't want five separate alerts for one hacker. The warehouse writer groups alerts into incidents:

  • The key is the attacker's IP. For distributed attacks with no single IP, it is the targeted user.
  • Alerts join the same incident while they keep arriving less than 10 minutes apart. This is a session window: a gap of 10 quiet minutes ends the session.
  • If an incident covers 2 or more ATT&CK tactics (for example Discovery and Credential Access), it is flagged multi-stage and raised one severity level.
ExampleThe kill-chain scenario produces a port scan (Discovery), injection probes (Initial Access), API probing (Reconnaissance), a brute force (Credential Access) and a successful login (Initial Access). It shows up as one critical, multi-stage incident instead of five unrelated alerts.

12AI summaries (the AI part from Lab 1)

For each incident, an LLM (Gemini, through its OpenAI-compatible API) writes a short plain-English summary: what happened, the likely goal, whether anything succeeded, and the first response steps.

  • Off the detection path: the summariser runs inside the dashboard service, so a slow or failing LLM never delays an alert.
  • Waits until things settle: it summarises only after the incident has been quiet for 8 s, and again only if the incident's content changes. This saves free-tier quota and avoids half-finished stories.
  • Privacy: only alert metadata is sent (rules, counts, tactics, times), never raw logs.
  • Fallback: with no API key, or when the API fails, a deterministic template writes the summary. The demo never depends on the internet.
  • Race fixed: the summary is stamped with the incident version it describes, so a summary written for an older version can't be shown as current.

14Self-evaluation: the platform grades itself

Because the simulator knows exactly what it launched, the system can check its own work. Security researchers evaluate detectors on labelled datasets such as CICIDS2017. We built that evaluation into the running system.

How an alert is matched to an attack

An alert belongs to a campaign if it names one of the campaign's IPs (or its target user, for per-user rules) and it first fired between the campaign's start and 2 minutes after its end.

  • Alerts matched to a malicious campaign are true positives.
  • Alerts matched to a benign campaign, or to nothing at all, are false positives.

Why precision and recall alone were not enough

Our attacks were designed to cross the thresholds, so at first precision and recall were 100%. That's true, but meaningless: it only proves the attacks were loud. We fixed this in two ways.

1. We added honest hard cases

CaseOutcomeWhyMitigation
Low-and-slow brute forcemissed4 guesses per minute never reaches 5 per 60 sLonger windows, or per-account baselines
IT inventory scanfalse alarmAn admin scan looks exactly like an attacker's scanAllow-list the admin subnet, or lower the severity for known assets
Office NAT login rushfalse alarmMany users behind one IP look like a password sprayAllow-list known NAT IPs, or require a higher ratio of failures to users

Now precision is about 85% and recall about 97.6%, and every miss and false alarm has a known cause.

2. We added metrics that actually vary

  • MTTD (mean time to detect): the time from campaign start to the first alert, about 0.53 s. This includes the time the attack itself needs to reach the threshold.
  • Attack seen before alert: how much of the attack had already happened when we alerted. Injection is caught at about 5%, because one request is enough. Scans are caught at about 55%, because 10 ports are needed. This is computed by an analytical query on the Parquet lake with partition pruning, so the lake is used for real analysis, not just storage.
  • Earlier than window close: how much sooner early alerting fired than a window-close alert would have, about 60–70 s.
  • Alert-reduction funnel: 1,248 attack events → 40 alerts → 26 incidents. Suppression and grouping are what stop analysts drowning in alerts.
Fair playGround truth travels on a separate topic that the processor never subscribes to. Detection cannot "peek at the answers".

15Pipeline health: proving the data is right

A data pipeline should be able to show that it isn't losing data. The pipeline-health panel checks three things.

  • Completeness (reconciliation): events delivered by the shippers = events in Kafka = events processed = rows in the lake. Comparing counts between stages is how real data teams catch silent loss. Result: 3,857 shipped = 3,857 in Kafka, 0 lost.
  • Freshness per layer: how far behind real time each layer is: detection about 70 ms, warehouse about 1 s, lake up to 30 s (its flush interval). Each layer makes a different trade-off, and the panel shows each one's consumer lag.
  • Storage: Parquet size compared with the raw JSON it replaced (about 5×), and the number of partitions.
A subtle bug we fixedThe panel once showed "2 events lost". Nothing was lost: we had read Kafka's count first and the shippers' count a moment later, and new events had arrived in between. Now the shippers are read before Kafka. Anything a shipper counts as delivered must already be in Kafka, so a gap would mean real loss.

18What is novel or interesting

Defended systems write the logs

Most student SIEMs have the attack generator write fake log lines directly. Ours sends real traffic, the victims log what they observe, and the kernel supplies source IPs. That is how real SIEMs are fed.

Built-in self-grading

Ground truth on an isolated topic, and a live scoreboard with MTTD, funnel, attack-seen-before-alert and honest precision/recall.

Honest hard cases

We deliberately included an attack we miss and two false alarms, each explained, instead of showing a misleading 100%.

Early alerting with correctness

Because every rule measures something that only grows, the system alerts in milliseconds and never has to retract, then refines the same alert ID.

Panes for sliding windows

Each event is stored once, not six times. This is a known stream-processing optimisation, implemented by hand.

Effectively-once results

At-least-once delivery, dedup, deterministic IDs and upserts, plus a commit protocol that recovers without re-alerting.

Lake used for analytics

The scoreboard runs a partition-pruned Parquet query, so the lake isn't just an archive.

Pipeline observability

Reconciliation across stages, freshness per layer, lag per consumer group, measured compression.

Chaos mode on demand

Five-minute demo

  1. Start Low-and-Slow first, because it takes about 3 minutes.
  2. Show background traffic: throughput moves, and there are no alerts.
  3. Brute force: an alert within about 100 ms, tagged T1110.001, which then escalates.
  4. Port scan and host sweep: the sensor sees what the website can't.
  5. Multi-stage intrusion: one critical incident with an AI summary.
  6. Turn on Unreliable network: the duplicate and late counters rise, and alert counts stay correct.
  7. Hard cases: low-and-slow was missed; the admin scan and office NAT raise false alarms, each explained.
  8. Scoreboard and pipeline health: MTTD, funnel, 0 lost, freshness, compression.
